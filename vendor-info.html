Digi-ID app/website introduction

What vendors need to know

Read time:
4 minutes

Digi-ID: Websites & Apps

Digi-ID lets users sign in by scanning or tapping a QR code and approving the request in a compatible app. It uses public key cryptography: a private key creates a digital signature that your server verifies. No DigiByte blockchain connection is required.

How a sign-in works:

  1. Your service creates a unique challenge, links it to the pending session, and displays a Digi-ID QR code.
  2. The user scans or taps the code and approves the request.
  3. The app sends a signed response and public Digi-ID address, which acts as the login identifier.
  4. Your server verifies the response and challenge, then grants access to the associated account and session.

What does integration involve?

Integration depends on your platform. A compatible plugin may reduce setup time; otherwise, the PHP and JavaScript examples provide a starting point. Review compatibility, dependencies, and maintenance before production use. The PHP sample includes a fixed, dated copy of an external cryptography library that should be reviewed and updated, and it limits login attempts to one per IP address at a time by default.

Your application must create sign-in requests, verify responses, and link the Digi-ID address to the correct account. You also need to design enrollment, recovery, and session handling.

Account recovery depends on the user’s wallet recovery phrase. If it is lost, the identifier cannot be recovered.

Can Digi-ID replace passwords?

Yes. Digi-ID can be used as the sign-in method or as an additional step after a password. Offering two sign-in choices does not automatically add a second security check.

If passwords are disabled for an account, users cannot choose weak or reused passwords, and your service has no password or password hash to store. Other account data and active sessions still require protection.

Security, Privacy & Setup

Can a sign-in response be reused?

Replay protection depends on your server. Use a fresh, unpredictable nonce (a value for one sign-in request), link it to the pending session, set an expiration, and reject it after use. Verify the signature and expected callback URL before granting access. ~90 seconds is a reasonable starting point for website sign-in; shorten or lengthen it to suit your application.

Can a Digi-ID QR code be relayed?

Yes. An attacker could present a real Digi-ID QR code from your site to another user and capture the session if they approve it.

Callback validation does not stop this because the request is genuinely for your site. Require a fresh approval for sensitive actions, and tell users to approve only codes on pages they opened themselves. Short nonce lifetimes help with stale or forwarded codes, but not live relay attacks.

Is signing in on a shared computer safe?

Digi-ID avoids typing a website password on that computer. It does not make the computer safe; an attacker could still capture the active session or data shown in the browser. Users should sign out when finished.

Can users share access or use multiple accounts?

Yes. Users can share a device or restore the same keys elsewhere. Your application may also allow one Digi-ID address to access multiple accounts, but it must manage account linking and selection.

What is the Digi-ID address derived from?

The address depends on the callback URI, so changing the domain, path, or host can produce a different address for the same user. Choose a stable callback URL before enrollment and plan for re-enrollment if it changes.

How do I collect contact details?

Digi-ID does not provide email, name, or delivery details. Collect them separately when needed. Its login identifier is pseudonymous, not anonymous, because your service can associate it with an account, activity, and user-provided information.

Do I need extra servers or a blockchain connection?

Digi-ID does not require a DigiByte node or external identity provider. Signature verification can run on your server, but the app must reach your callback endpoint. Use HTTPS in production; plain HTTP is for development only with &u=1 appended.
